# 온케어 추천·배정 로직 검토

팀 프로젝트 온케어(`oncare_backend`)에서 추천·배정을 담당한 코드를 다시 읽고, 이 프로젝트로 가져온 것과 고친 것을 정리한 문서입니다.

검토한 코드
- `AutoAssignService` — 필수 조건 필터 (`filterCareworker`, `canWork`, `isBusy`), 묶음 신청 필터
- `CareWorkerRecommendationService` — 점수 계산과 정렬 (`recommendCandidates`)
- `CareWorkerReportService.assignCareworker` — 관리자가 후보 중 한 명을 골라 배정
- `CareWorkerReportRepository.countCompletedWork` — 최근 30일 근무 횟수 집계

## 1. 그대로 가져온 것

| 항목 | 내용 |
|---|---|
| 필수 조건 | 근무 상태, 선호 성별, 근무 가능 시간 안에 방문 시간이 들어오는지, 같은 날 겹치는 일정(취소 제외)이 없는지 |
| 거리 점수 | 50점, 0km 만점, 25km 이상 0점, 그 사이 직선 감소 |
| 근무량 점수 | 30점, 최근 30일(오늘 포함) 완료 방문 0회 만점, 20회 이상 0점 |
| 연속 담당 점수 | 20점, 같은 수급자를 방문한 횟수 기준 |
| 동점 처리 | 총점 → 거리 가까운 순 → 근무 적은 순 → 번호 순 |
| 근무량 집계 | `GROUP BY` 한 번으로 후보 전체를 집계 (온케어에서도 이미 이렇게 되어 있던 부분) |

## 2. 허술했던 점과 개선

| # | 온케어 | 문제 | 이 프로젝트 |
|---|---|---|---|
| 1 | `careworkersRepository.findAll()` 후 메모리에서 상태·성별 필터 | 휴직·퇴사자까지 전부 읽음 | 상태·성별은 컬럼 비교라 DB 조건으로 거름 (`findByStatusAndGender`) |
| 2 | `canWork`, `isBusy` 가 보호사마다 쿼리 | 후보 N명이면 쿼리 2N번 | 근무 가능 시간·그날 예약을 `IN` 조건으로 한 번씩 조회 후 보호사별로 나눔 |
| 3 | 연속 담당 횟수: 보호사마다 근무 기록 전체 조회 + 기록마다 방문 요청 지연 로딩 | 후보 N명, 완료 기록 M건이면 N + M번 | `GROUP BY` 집계 쿼리 한 번 |
| 4 | 상태를 문자열로 비교 (`"근무중"`, `"신청"`, `"완료"`) | 오타가 나도 컴파일 때 못 잡음 | enum (`CaregiverStatus`, `VisitRequestStatus`, `ReservationStatus`) |
| 5 | 좌표를 못 구하면 0, 0 으로 저장하고 추천 때 걸러냄 | 잘못된 데이터가 저장된 뒤에야 발견 | 등록 시 좌표 필수 + 범위 검증 (`@NotNull`, `@DecimalMin/Max`) |
| 6 | 요청이 없거나 이미 배정된 요청이면 빈 목록 반환 | "후보가 없음"과 "요청이 잘못됨"을 구분할 수 없음 | 404 `VISIT_REQUEST_NOT_FOUND`, 409 `VISIT_REQUEST_NOT_ASSIGNABLE` |
| 7 | 이중 for 문으로 직접 자리를 바꾸는 정렬 | O(n²), 정렬 기준을 읽기 어려움 | `Comparator.comparingDouble(...).thenComparing(...)` |
| 8 | 서비스 안에서 `LocalDate.now(ZoneId.of("Asia/Seoul"))` | 테스트에서 "오늘"을 고정할 수 없음 | `Clock` 빈을 주입받아 사용 |
| 9 | 거리 계산(`HaversineService`)이 `@Service` + `@Transactional` | DB 를 안 쓰는 계산에 트랜잭션이 열림 | 정적 메서드 `GeoDistance.km` |
| 10 | 점수 계산이 서비스 클래스 하나에 모여 있고 테스트 없음 | 항목을 바꾸려면 서비스 전체를 고쳐야 함 | `ScorePolicy` 구현체 3개로 분리, 경계값 단위 테스트 |
| 11 | 연속 담당 1회는 0점 (2회부터 5점) | 한 번 가 본 보호사와 처음 가는 보호사가 같은 점수 | 1회부터 5점, 4회 이상 20점 (정책 변경) |

### 쿼리 수 측정 (2, 3번 개선 결과)

`RecommendationQueryCountTest`에서 같은 데이터로 두 방식을 실행하고 Hibernate 통계(`getPrepareStatementCount`)로 쿼리 수를 셌습니다. 온케어 방식은 `OncareStyleCandidateLoader`(테스트 코드)에 같은 조회 구조로 옮겨 두었고, 두 방식의 추천 결과가 같은지도 함께 확인합니다.

| 후보 수 | 온케어 방식 | 집계 쿼리 방식 |
|---|---|---|
| 10명 | 54회 | 6회 |
| 100명 | 504회 | 6회 |

- 온케어 방식은 `4 + 5N`회로 후보 수에 비례해 늘어납니다 (보호사마다 근무 가능 시간 1 + 그날 일정 1 + 근무 기록 전체 1 + 완료 기록 2건의 방문 요청 지연 로딩 2).
- 실제 온케어는 보호사마다 탈퇴 여부 확인(`activeUserCheck`)도 해서 이보다 더 많습니다. 이 프로젝트에는 회원 테이블이 없어 그 부분은 재현하지 않았습니다.
- 개선 후 6회: 방문 요청(수급자 함께 조회) 1, 보호사 1, 근무 가능 시간 1, 그날 예약 1, 근무량 집계 1, 연속 담당 집계 1.
- H2 기준 쿼리 "수"입니다. 응답 시간(p95)은 MySQL + 보호사 1,000명 데이터로 따로 잴 예정입니다.

## 3. 배정 확정의 빈틈과 개선

`assignCareworker`에는 배정 확정 단계의 빈틈이 있었습니다.

| 온케어 | 문제 | 이 프로젝트 |
|---|---|---|
| 관리자가 고른 날짜는 배정 직전에 다시 검증하지 않음 (묶음의 다른 날짜만 `isAvailable`로 확인) | 추천과 배정 사이에 다른 배정이 들어오면 겹치는 근무가 생김 | `ReservationWriter`가 추천과 같은 필터로 확정 직전에 다시 검증 |
| 요청 상태 확인 → 근무 기록 저장 사이에 락·제약 없음 | 같은 보호사에게 동시 배정 시 겹치는 근무 | 보호사 비관적 락 + 유니크 제약 (방법 B + A) |
| 같은 요청을 두 관리자가 동시에 배정해도 막는 장치 없음 | 한 요청에 근무 기록 두 건 | `VisitRequest`의 `@Version` |

동시 요청 100건 실험 결과는 README의 "트러블슈팅 ①"에 있습니다.

## 4. 묶음 신청 (`requestGroup`)

온케어는 여러 날짜를 한 번에 신청하면 모든 날짜에 갈 수 있는 보호사를 우선 추천하고, 배정할 때 나머지 날짜도 같은 보호사로 배정했습니다. 기능은 가져오고 구조는 고쳤습니다.

| 온케어 | 문제 | 이 프로젝트 |
|---|---|---|
| 날짜마다 필터 전체를 다시 돌리고 이중 for 문으로 교집합 | 쿼리가 날짜 수 × 2N번 | 묶음의 요일·날짜를 `IN`으로 한 번씩 조회하고, 보호사마다 **모든 날짜에 대해** 기존 필터를 `allMatch`. 날짜 1·7·14개 모두 6회 (`RecommendationQueryCountTest`) |
| 고른 날짜는 재검증하지 않고 나머지 날짜만 `isAvailable` 확인 | 추천과 배정 사이 다른 배정이 끼면 겹침 | `ReservationWriter.confirmGroup`이 **모든 날짜**를 확정 직전에 다시 검증 |
| 날짜별로 따로 저장 | 중간에 실패하면 일부 날짜만 배정된 채 남음 | 트랜잭션 하나(`READ COMMITTED`)로 전부 아니면 전무. 보호사 락은 날짜 수와 상관없이 1번 |
| 동시성 고려 없음 | — | 락 전략 4개 모두 지원. Redisson은 날짜별 락을 **날짜 오름차순으로** 잡아 묶음끼리의 데드락 방지 |

- 동시성 확인 (`GroupReservationConcurrencyTest`, H2): 날짜를 일부씩 공유하고 시간이 겹치는 묶음 21개 동시 확정 → 1개 성공, 저장된 예약 2건(성공한 묶음의 날짜 수), 겹침 0. 묶음 1개 + 그 날짜에 겹치는 단건 50개 → 1건만 성공, 묶음은 전부 배정되거나 하나도 배정되지 않음.
- 범위 밖: 날짜마다 다른 시간대, 일부 날짜만 가능한 보호사 추천, 반복 규칙 입력, 묶음 수정.

## 5. 아직 가져오지 않은 것

| 기능 | 온케어 구현 | 판단 |
|---|---|---|
| 배정 수락·거절 (`배정` → `배정완료`) | 관리자가 배정하면 보호사가 수락해야 확정 | 로그인이 없어 "보호사 본인"을 구분할 수 없으므로 제외. 이 프로젝트는 관리자 확정 = 예약 확정 |
| 가입 승인·탈퇴 여부 | 승인 전·탈퇴 회원 제외 | 로그인 기능을 범위에서 뺐으므로 제외 |
| 방문 시간 변경 문의 (`excludeRequestNo`) | 같은 방문의 기존 근무는 겹침으로 보지 않음 | 범위 밖 |
