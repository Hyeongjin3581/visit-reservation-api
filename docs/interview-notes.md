# 면접 대비 질문과 답

이 프로젝트에서 나올 만한 질문과, 코드에서 근거를 찾을 수 있는 답을 정리했습니다. 답을 외우기보다 괄호 안의 파일을 열어 보고 자기 말로 바꿔 보는 것을 권합니다.

## 1. 프로젝트 소개

**Q. 어떤 프로젝트인가요?**
요양보호사 추천과 방문 예약 확정 API입니다. 팀 프로젝트 온케어에서 제가 맡았던 추천·배정 로직의 아쉬운 점 두 가지, 즉 보호사마다 따로 조회하던 N+1 구조와 동시 배정 검증이 없던 점을 혼자 다시 설계해서 고치고, 전후를 수치로 비교했습니다.

**Q. 개선 전 수치(504회 등)는 온케어를 직접 잰 건가요?**
아닙니다. 온케어와 같은 조회 구조를 이 프로젝트 엔티티로 테스트 코드(`OncareStyleCandidateLoader`)에 옮겨서, 같은 데이터로 두 방식을 비교했습니다. 온케어 실제 코드는 보호사마다 탈퇴 여부 확인 쿼리가 하나 더 있어서 실제로는 더 많습니다.

## 2. 추천과 N+1

**Q. N+1이 어디서 생겼나요?**
온케어는 후보 보호사 한 명마다 근무 가능 시간 1번, 그날 일정 1번, 근무 기록 전체 1번을 조회했고, 근무 기록마다 방문 요청을 지연 로딩했습니다. 완료 기록이 보호사당 2건이면 `4 + 5N`번입니다. 후보 100명이면 504번입니다.

**Q. 어떻게 고쳤나요? 왜 fetch join이 아니라 그렇게 했나요?**
종류별로 한 번씩, 후보 전체를 대상으로 조회했습니다. 근무 가능 시간과 그날 예약은 `IN` 조건으로 가져와 `groupingBy`로 보호사별로 나누고, 근무량과 연속 담당 횟수는 `GROUP BY` 집계로 숫자만 가져옵니다. fetch join은 연관된 행을 전부 끌고 오는데, 근무량은 행이 아니라 개수만 필요해서 집계가 더 맞습니다. (`RecommendationService`, `ReservationRepository`)

**Q. 쿼리 6번은 각각 뭔가요?**
방문 요청(수급자 함께 조회) 1, 1차 후보 보호사 1, 근무 가능 시간 1, 그날 예약 1, 근무량 집계 1, 연속 담당 집계 1입니다. 후보가 1,000명이어도 6번입니다.

**Q. 방문 요청을 조회할 때 `join fetch`를 쓴 이유는요?**
바로 다음에 수급자의 좌표와 선호 성별을 쓰기 때문입니다. 그냥 `findById`로 읽으면 수급자는 지연 로딩이라 쿼리가 한 번 더 나갑니다.

**Q. 필터를 SQL 조건으로 다 하지 않고 객체로 나눈 이유는요? 손해는 없나요?**
필터와 점수를 DB 없이 단위 테스트할 수 있고, 조건을 추가할 때 구현체만 추가하면 됩니다. 손해는 1차 후보를 메모리로 다 가져온다는 점입니다. 보호사가 수만 명이 되면 위경도 범위(bounding box)나 근무 가능 시간 조건을 SQL로 먼저 걸러서 가져오는 양을 줄여야 합니다. 그래서 근무 상태와 성별처럼 컬럼 하나로 판단되는 조건은 이미 DB에서 거릅니다.

**Q. 점수 정책은 어떻게 테스트했나요?**
경계값 단위 테스트입니다. 거리 0km 50점, 12.5km 25점, 25km 이상 0점처럼 각 정책의 시작·중간·끝을 확인하고, 만점의 합이 100점인지도 테스트합니다. (`ScorePolicyTest`)

## 3. 예약 확정과 동시성

**Q. 시간을 왜 30분 단위로만 받나요?**
DB 유니크 제약으로 중복 예약을 막으려면 같은 시간대가 항상 같은 값이어야 합니다. 10:00과 10:07을 모두 허용하면 사실상 같은 시간대인데도 다른 값이 돼서 제약이 의미가 없어집니다.

**Q. 유니크 제약만으로는 왜 부족한가요?**
`(보호사, 날짜, 시작 시간)`이 같아야만 막습니다. 10:00~12:00과 10:30~12:30은 겹치지만 시작 시간이 달라서 둘 다 들어갑니다. 동시 요청 100건 실험에서 4~5건이 들어가고 겹친 쌍이 6~10개 생겼습니다. 실행마다 숫자가 달라지는 것 자체가 경쟁 상태(race condition)라는 증거입니다. 그래서 겹침 검사는 락을 잡은 상태에서 해야 합니다.

**Q. 그래도 유니크 제약을 남겨 둔 이유는요?**
락 코드에 실수가 있거나 락을 우회하는 경로가 생겨도, 같은 시작 시간 중복만큼은 DB가 마지막에 막아 주는 안전장치입니다.

**Q. 취소된 예약이 슬롯을 차지하던 문제는 어떻게 풀었나요?**
유니크 제약에 `active_slot` 칸을 추가했습니다. 살아 있는 예약은 TRUE, 취소하면 NULL입니다. MySQL 유니크 인덱스는 NULL을 서로 다른 값으로 취급해서, 취소된 예약끼리는 충돌하지 않고 같은 슬롯에 새 예약이 들어갈 수 있습니다. (`Reservation`)

**Q. 비관적 락과 낙관적 락의 차이는요?**
비관적 락은 충돌이 날 거라고 보고 먼저 잠급니다. `SELECT ... FOR UPDATE`로 보호사 행을 잠그면 같은 보호사에 대한 다른 확정은 기다렸다가 앞사람이 커밋한 예약을 보고 겹침을 판단합니다. 낙관적 락은 잠그지 않고 진행하다가, 커밋할 때 버전이 바뀌었으면 실패시키고 다시 시도합니다.

**Q. `@Version`은 어디에 왜 붙였나요?**
세 곳에 있고 역할이 다릅니다.
- `Caregiver`: 방법 C용. 확정할 때마다 버전을 강제로 올려서(`OPTIMISTIC_FORCE_INCREMENT`) 같은 보호사에 동시에 들어온 확정 중 하나를 실패시킵니다.
- `VisitRequest`: 같은 요청을 서로 다른 보호사로 동시에 배정하는 경우를 막습니다. 보호사가 다르면 보호사 락으로는 서로 안 막히기 때문입니다.
- `Reservation`: 같은 예약을 동시에 수정하는 경우(취소와 완료가 동시에 들어옴)를 막습니다.

처음에는 `Reservation`에만 `@Version`을 두고 낙관적 락 실험에 쓰려고 했는데, 새 예약끼리의 충돌은 서로 다른 행을 새로 만드는 것이라 기존 행의 버전으로는 막을 수 없다는 걸 알고 보호사 쪽으로 옮겼습니다.

**Q. 낙관적 락 재시도를 왜 트랜잭션 바깥에서 하나요?**
버전 충돌이 난 트랜잭션은 롤백 전용 상태가 돼서 그 안에서는 다시 시도할 수 없습니다. 새 트랜잭션으로 처음부터 다시 읽어야 앞사람이 커밋한 예약이 보이고, 겹침 검사에서 걸립니다. 그래서 `ReservationService`에는 `@Transactional`이 없고, 트랜잭션은 `ReservationWriter.confirm`에만 있습니다. (`OptimisticLockStrategy`)

**Q. Redis 분산 락에서 주의한 점은요?**
순서입니다. 락 획득 → 트랜잭션 시작 → 커밋 → 락 해제 순서여야 합니다. 트랜잭션 안에서 락을 풀면 커밋 전에 다음 요청이 락을 잡고, 아직 커밋되지 않은 예약을 못 봐서 겹침 검사를 통과할 수 있습니다. 또 만료 시간(leaseTime)을 주지 않아서, 작업이 길어지면 Redisson 워치독이 락을 자동으로 연장합니다. 락 키는 `lock:caregiver:{id}:{날짜}`라서 같은 보호사라도 다른 날짜 예약은 기다리지 않습니다. (`RedissonLockStrategy`)

**Q. 4가지 중 왜 비관적 락을 기본으로 했나요?**
서버 1대 기준으로 추가 인프라 없이 겹침까지 막고, 재시도 로직이 필요 없어 단순합니다. 잠그는 범위가 보호사 한 명이라 경합도 작습니다. 서버를 여러 대로 늘리면 Redis 분산 락으로 설정만 바꾸면 됩니다.

**Q. 동시성 테스트는 어떻게 만들었나요?**
스레드 32개짜리 풀에 확정 요청 100개를 넣고, `CountDownLatch`로 출발선에 세웠다가 한꺼번에 출발시킵니다. 끝나면 성공 수, DB에 저장된 예약 수, 겹치는 예약 쌍의 수를 셉니다. 테스트에 `@Transactional`을 붙이면 모든 스레드가 각자 트랜잭션이라 서로의 데이터를 못 보고 롤백도 안 되므로, 실제로 커밋하고 테스트마다 데이터를 지웁니다. (`ConcurrencyTestSupport`)

**Q. H2로 동시성 테스트를 해도 믿을 수 있나요?**
락이 걸리는 방식은 DB마다 다르기 때문에 H2 결과만으로는 부족합니다. 그래서 같은 테스트를 MySQL에서 돌리는 `mysqlTest` 작업을 만들고, GitHub Actions에서 MySQL 컨테이너로 실행되게 했습니다. 예를 들어 MySQL은 유니크 인덱스에 갭 락을 걸어서, 방법 A에서 데드락 실패가 섞여 나올 수 있습니다.

## 4. 기타

**Q. `Clock`을 주입받는 이유는요?**
근무량 점수가 "오늘 포함 최근 30일" 기준이라, 서비스 안에서 `LocalDate.now()`를 직접 부르면 테스트에서 날짜를 고정할 수 없습니다. 서버 시간대와 상관없이 한국 날짜로 계산하는 효과도 있습니다.

**Q. 에러 응답은 어떻게 통일했나요?**
`ErrorCode` enum에 상태 코드와 메시지를 모으고, `@RestControllerAdvice`에서 `{code, message}` 형식으로 바꿉니다. 온케어는 요청이 없을 때 빈 목록이나 `false`를 돌려줘서 원인을 알 수 없었는데, 여기서는 404·409로 구분합니다.

**Q. 아쉬운 점은요?**
MySQL에서 직접 잰 응답 시간과 HTTP 부하 테스트(k6)가 없습니다. 비관적 락이 보호사 단위라 같은 보호사의 다른 날짜 예약끼리도 기다리는 점도 개선할 수 있습니다. 예를 들어 보호사·날짜 단위의 잠금용 행을 따로 두는 방법이 있습니다.
